# Known-failing "path config" pairs for tests/run_examples.sh, one per
# line, path relative to the repo root, config is "on" or "off".
#
# Each entry below was individually diagnosed (not just observed) when
# this file was written -- see the reason on each line.

# --- Slow, not broken. Both of these were registered here as "infinite
# runs: sc_start() with no stop time and no code path that ever halts".
# That diagnosis was wrong for both, and finding out why turned up a
# real library defect:
#
#  * ct/cttutorial genuinely never terminated, but not because it was
#    unbounded -- DDE::filter's adaptive-step solver never adapted its
#    step. `step` was assigned once in init() and never changed, so a
#    step that failed the error tolerance re-requested the same two
#    sample times forever, spinning at 100% CPU with simulated time
#    standing still at t=100us. Fixed in the library (see
#    dde_process_constructors.hpp); the model now completes, in ~59s.
#  * mi/ir_uwb_radar was never stuck at all. It advances steadily at
#    ~1.67s of wall time per 100ns of model time and reaches its
#    END_T of 11000ns in about three minutes: an 8th-order filter
#    solved twice per 25ps step, 440,000 steps.
#
#    Superseded in 2d: it now fails immediately instead, with
#      top1.ir_channel1.scale123: tried to advance its local time
#      backwards, to 425 ps, but it is already at 900 ps
#    from the guard added to the CT and DDE time advance. That is not a
#    new defect -- the same backwards wait was there before, where an
#    unsigned sc_time turned it into a wait of ~213 days of simulated
#    time, parking the process silently for the rest of the run. The
#    model reaches its end time either way, which is why the three-minute
#    reading above was accurate; what it does not say is that a process
#    dropped out along the way. Something upstream of scale123 emits
#    sub-signals whose intervals go backwards, most likely the parallel
#    CT::shift branches in ir_channel, whose different delays put the
#    branches on different interval grids. Diagnosing that is CT
#    interval-alignment work, not a harness matter.
#
# Both now finish; both exceed this harness's 30s per-example budget, so
# they stay registered. Raising TIMEOUT would let them pass at the cost
# of making ir_uwb_radar the critical path of the whole suite (~3min vs
# the ~105s the other 30-odd examples take together), which is a
# trade-off worth making deliberately rather than by default.
ct/cttutorial on
ct/cttutorial off
mi/ir_uwb_radar on
mi/ir_uwb_radar off

# --- The FMU that mi/cruisecontrol loads (fmi2/car.fmu) is
# Co-Simulation-only -- there is no ModelExchange element in its
# modelDescription.xml -- but the code path ct_wrappers.hpp drives in
# sim_support.h requires ModelExchange: "error: No ModelExchange element
# found in model description. This FMU is not for Model Exchange." A
# real defect in the wrapper's FMU-loading logic, not in the XML parser
# (D15, fixed in step 0.6: the parser is confirmed working end to end,
# unzipping car.fmu and reading fmiVersion=2.0, modelName=car out of it).
#
# Separately, on a host where GDB cannot get a controlling terminal
# (this dev sandbox is one: gdbwrap's spawned xterm shows only "warning:
# GDB: Failed to set controlling terminal: Operation not permitted" and
# then hangs, leaving a real un-closeable window on the desktop), this
# config must not be run at all -- set FORSYDE_SKIP_GDB in the
# environment and the harness skips it rather than opening another one.
# Also unfixed: gdbwrap never kills its spawned `gdb --interpreter=mi`
# child on any exit path.
#
# All of this belongs to the Phase-1b wrapper rework rather than to
# standalone patches. The "off" configuration does not hit any of it:
# this harness builds "off" by overriding CFLAGS wholesale, which also
# strips -DFORSYDE_WITH_GDB -DFORSYDE_WITH_FMI, so it silently takes the
# non-wrapper code path instead. That is a limitation of this interim
# harness, not evidence the "off" build exercises the wrapper safely.
mi/cruisecontrol on

# --- sdf/mp3decoder builds and decodes correctly, but only in the
# introspective configuration, for a harness reason rather than a model
# one. This example's Makefile sets -DFORSYDE alongside
# -DFORSYDE_INTROSPECTION, and -DFORSYDE is what selects its ForSyDe
# integration code path over the standalone-decoder one (see the #ifdef
# FORSYDE blocks in readBitstreamAndExtractFrames.cpp and
# mergeChanules.cpp). This harness produces the "off" configuration by
# overriding CFLAGS wholesale, which strips *every* macro the example's
# own Makefile adds, not introspection alone -- so the "off" build loses
# -DFORSYDE too and fails on mon_debug_info.
#
# That wholesale override is deliberate and worth keeping: it is also
# what stops mi/cruisecontrol's "off" build from requiring libmigdb and
# libxml2 in the core CI job. The same limitation is described at more
# length on the mi/cruisecontrol entry above. Fixing it properly means
# per-example control over which macros the "off" pass removes, which
# belongs with a real build system rather than this interim harness.
sdf/mp3decoder off
